# Use Case

開發新功能的依據。一份文件描述一個機制，格式為六欄位（機制名稱／使用角色／前置條件／使用情境／替代情境／後置條件），其中替代情境就近附在被觸發的主流程步驟下，後置條件寫成使用情境結尾的「完成」區塊。

| 機制 | 狀態 | 說明 |
| --- | --- | --- |
| [單日行程分享](single-day-share.md) | 草稿 | 出發前一晚把明天的行程送進旅伴群組；旅途中改完可再次分享 |
| [行程展示分享](showcase-share.md) | 草稿 | 把行程做成直式展示圖張貼社群，將非同行的觀看者導向工具 |
| [貼地圖分享連結定位天氣](map-link-location.md) | 草稿 | 貼 Google 地圖分享連結，讀出地點名稱確認，天氣以該地點查詢；不再用地名猜位置 |

## 為什麼這兩個機制要分開

兩者都是「把行程送出去」，但對象與目的相反，設計取捨也相反——資訊密度、是否夾帶行程資料、回訪入口指向哪裡都不同。混成一個機制會讓兩邊都失焦。對照表見 [行程展示分享](showcase-share.md#與單日行程分享的關鍵差異)。

## 這批 use case 的來源

2026-09-13 的討論。起點是兩位使用者回報「喜歡這個產品是因為簡單輸入就能匯出行程，以及方便截圖分享行程」，由分享情境切入展開。討論中確認的幾個事實：

- 分享連結（`/v/` 模式）中觀看者的編輯只保存在該裝置，不會同步給其他人
- 分享連結的 PIN 碼不具保護作用——行程資料本就編碼在網址中，PIN 只增加開啟阻力
- 分享連結目前會夾帶訂位號碼等敏感欄位
- 觀看者無法用同一台裝置掃描自己畫面上的 QR code，回訪入口不能只做 QR
