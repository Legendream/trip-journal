# Use Case

開發新功能的依據。一份文件描述一個機制，格式為六欄位（機制名稱／使用角色／前置條件／使用情境／替代情境／後置條件），其中替代情境就近附在被觸發的主流程步驟下，後置條件寫成使用情境結尾的「完成」區塊。

| 機制 | 狀態 | 說明 |
| --- | --- | --- |
| [單日行程分享](single-day-share.md) | 草稿 | 出發前一晚把明天的行程送進旅伴群組；旅途中改完可再次分享 |
| [行程展示分享](showcase-share.md) | 草稿 | 把行程做成直式展示圖張貼社群，將非同行的觀看者導向工具 |
| [貼地圖分享連結定位天氣](map-link-location.md) | 草稿 | 貼 Google 地圖分享連結，讀出地點名稱確認，天氣以該地點查詢；不再用地名猜位置 |
| [分組行程建立](group-trip-setup.md) | 草稿 | 旅伴分組、分頭出發又會合時，行程建立者以成員代號標記每段行程的對象 |
| [依身分檢視行程](group-trip-view.md) | 草稿 | 旅伴選擇自己的成員代號，預設只看自己的行程，可切換全部檢視 |
| [指定對象的集合](group-meeting.md) | 草稿 | 集合可指定通知對象，多個集合並存不互相覆蓋 |
| [記帳分擔預設](group-expense-default.md) | 草稿 | 分擔成員預設為付款人當日同行的人，結算仍全體共用 |

## 為什麼這兩個機制要分開

兩者都是「把行程送出去」，但對象與目的相反，設計取捨也相反——資訊密度、是否夾帶行程資料、回訪入口指向哪裡都不同。混成一個機制會讓兩邊都失焦。對照表見 [行程展示分享](showcase-share.md#與單日行程分享的關鍵差異)。

## 這批 use case 的來源

2026-09-13 的討論。起點是兩位使用者回報「喜歡這個產品是因為簡單輸入就能匯出行程，以及方便截圖分享行程」，由分享情境切入展開。討論中確認的幾個事實：

- 分享連結（`/v/` 模式）中觀看者的編輯只保存在該裝置，不會同步給其他人
- 分享連結的 PIN 碼不具保護作用——行程資料本就編碼在網址中，PIN 只增加開啟阻力
- 分享連結目前會夾帶訂位號碼等敏感欄位
- 觀看者無法用同一台裝置掃描自己畫面上的 QR code，回訪入口不能只做 QR

## 分組旅行這批 use case 的來源

2026-10-05 的討論。起點是行程建立者自己 11 月的旅行：兩組旅伴分頭出發（鹿兒島、福岡），在屋久島會合，再分頭回程。討論中確定的事：

- 記帳、集合全體共用：讓全體成員使用同一個行程 App
- 行程對象、集合對象、分擔成員一律記錄成員代號；組別只是勾選的捷徑，所以成員中途換組不需要另外的機制
- 成員代號由行程建立者自訂、建立後沿用，不另設內部編號（行程 App 內無法修改成員名單）
- 不論有無分組，旅伴都在首次開啟行程 App 時選擇自己的成員代號（只有一條程式路徑）；只有發起者能取消集合；記帳不新增日期欄位
- 個人檢視只是顯示偏好，不是存取控制（行程資料寫在行程 App 中，同步資料庫的規則為全公開讀寫）
