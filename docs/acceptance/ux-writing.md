# 驗收條件：產生器文案整理（UX Writing）

> 狀態：已確認範圍（Claire 2026-11-13：四個步驟全部做）｜步驟一分頁採方案 A（從使用者的處境出發），Claire 尚未明確選 A 或 B，PR 前再確認
>
> 開發五站的站①產物。實作在分支 `fix/generator-ux-writing`。

## 範圍

- **做**：產生器畫面上的文字——`generator/index.html`、`generator/generator-app.js`、`generator/group-ui.js` 裡使用者看得到的標題、說明、按鈕、提示訊息。
- **不做**：AI 整理指令（`PARSE_PROMPT`、`GROUP_SECTION_TEMPLATE`）、行程 App 樣板、落地頁 `index.html`、版面與配色、任何行為。

## 設計決定

| # | 決定 | 理由 |
|---|---|---|
| 1 | 四個步驟各只有一個名字：建立行程／編輯行程／挑選顏色／分享行程。步驟列、頁面標題、底部頁碼都用它；提到第幾步一律寫「步驟 2」。步驟一的按鈕只寫它做什麼（匯入行程、建立空白行程 →、打開這份行程 →） | 原本同一步有三種叫法（補齊資料、確認與微調行程、步驟二）；「匯入行程 → 進入步驟二」其實不會換頁 |
| 2 | 步驟一三個分頁改成使用者的處境：我有草稿／從零開始／繼續修改（手機寬度一行放得下四個字，所以不用更長的說法） | 使用者不用先把「我的情況」翻譯成「該用哪個方法」；「還原」聽起來像復原備份 |
| 3 | 兩種分享方式各只有一個名字：「分享連結」與「進階版」 | 原本有一行分享連結、專屬分享網址、方案 A、進階模式、方案 B、進階部署等叫法 |
| 4 | 行程裡的項目一律叫「景點」，每天的標題一律叫「這天的標題」 | 跟行程 App 一致（App 用「新增景點」「改這天的標題」） |
| 5 | 提到 App 的分頁，照 App 實際名稱寫：「清單」裡的「打包」「購物」「注意事項」 | 原本寫「打包」分頁，App 裡找不到 |

## 驗收 checklist

1. 步驟列、頁面標題、底部頁碼，同一步只用一個名字；按鈕說的動作和實際行為一致
2. 兩種分享方式在步驟 3、步驟 4、比較表裡各只用一個名字
3. 畫面上沒有內部或技術用語：MECE、SOP、校稿／出版、Prompt、API Key、解析、cache key、「系統」
4. 產生器提到的 App 分頁名稱與 App 實際名稱一致
5. 沒有行銷式說法（精心調配、完整解鎖等）；同一個畫面不重複同一句話
6. 每個欄位的標籤說得出它是什麼（例：「城市列表」其實是副標）
7. 行為不變：守護清單 G1–G15 不受影響；三支必跑檢查通過
8. 只動上面「範圍」列的檔案與文字
